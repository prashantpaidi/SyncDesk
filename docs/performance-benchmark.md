# Redis Performance Benchmark

Before/after benchmark for caching the dashboard metrics endpoint with Redis
(cache-aside). Every number below was **measured** on the machine described
below; nothing is estimated. Scripts: [`../performance/`](../performance/).

## Environment

| Item | Value |
|---|---|
| CPU | 2 vCPU — Intel Core Processor (Haswell, no TSX), virtualised VPS |
| RAM | 3.7 GiB total |
| OS | Linux 7.0.0-28-generic, x86_64 |
| Java | OpenJDK 21.0.12.1 |
| PostgreSQL | 16.15 (`postgres:16-alpine`) |
| Redis | 7.4.11 (`redis:7-alpine`) |
| k6 | v2.3.0 |
| Dataset | 100,000 tickets + 200,000 comments (generated by `DataSeeder`) |
| Backend | `java -Xmx640m -jar` (Hibernate `ddl-auto=update`, Hikari `maximum-pool-size=3`) |

Only the PostgreSQL and Redis containers were running. The backend was run
directly as a jar (`-Xmx640m`), and the **frontend was not running**. No other
heavy containers or processes were active during the runs.

## Endpoint

```
GET /api/dashboard/metrics
Authorization: Bearer <JWT>
```

Returns the aggregate snapshot (total, count by status, count by priority,
unassigned). It executes three aggregate queries:

1. `select status, count(*) from tickets group by status`
2. `select priority, count(*) from tickets group by priority`
3. `count(*) where assigned_to_id is null`

On a cache hit none of these run — a single Redis `GET` replaces them.

## Load profile

Identical profile for both scenarios (same dataset, endpoint, credentials,
duration and **offered load**), so latency is directly comparable:

- Executor: `constant-arrival-rate`, **15 requests/s**
- Warm-up: 15 s, Sustained: 45 s (60 s total)
- `preAllocatedVUs: 10`, `maxVUs: 50`
- 3 runs per scenario; the **median run** is reported
- Threshold `http_req_failed: rate<0.01`

15 req/s was chosen because it is the highest rate at which the **uncached**
backend is not saturated on this 2-vCPU box (its uncached single-request latency
is ~110 ms, and the sustained p50 is ~120 ms). Higher concurrency overloads the
uncached path and makes the comparison meaningless.

The latency figures below are for the dashboard request itself (a custom k6
trend, `dashboard_metrics_duration`), so the `setup()` login request does not
pollute them.

## Improvement (median, same offered load)

| Metric | Baseline | Redis | Improvement |
|---|---|---|---|
| p50 latency | 123.11 ms | 5.38 ms | **~23× faster** (95.6% lower) |
| p95 latency | 335.30 ms | 9.56 ms | **~35× faster** (97.2% lower) |
| p99 latency | 551.57 ms | 20.42 ms | **~27× faster** (96.3% lower) |
| Error rate | 0.00% | 0.00% | unchanged |

Database work avoided per cache hit: **3 aggregate queries** over the 100k-row
`tickets` table (the two `GROUP BY` scans and the unassigned count).

## Cache behavior

- **Cache name / key:** `dashboardMetrics` / Redis key `dashboardMetrics::global`.
- **TTL:** 60 s (`syncdesk.cache.dashboard-ttl`), a backstop only.
- **Invalidation:** ticket create / status change / assign / delete evict the
  entry eagerly (`@CacheEvict`); comments do not (they do not affect ticket
  aggregates).
- **Redis keyspace during the cached runs:** 103,081 hits vs 35 misses
  (**99.97% hit ratio**) — the misses are the initial cold fills after each
  `FLUSHALL` and TTL expiries.

### Cold vs warm cache

Redis does **not** make the first request faster — the first request is a miss
and still runs the three aggregate queries. Measured single request against an
emptied cache (`SCENARIO=cold`, cache flushed first):

| State | Latency |
|---|---|
| Cold (empty cache, steady state) | ~104 ms (104.76 ms / 103.54 ms) |
| Cold (first request after JVM start, JIT cold) | 1210 ms |
| Warm (cache hit) | ~5.4 ms |

So a cold request costs about the same as the uncached baseline (~110 ms); all of
the gain comes from **subsequent** requests.

### Throughput ceiling (indicative)

Under a saturating `constant-vus` profile (20 VUs, 60 s) the **baseline** was
server-bound at **19.0–19.8 req/s**, while the **cached** backend reached
**398–687 req/s**. The cached figure is a **lower bound**: at that throughput k6
and the JVM saturated the 2-vCPU box (1-minute load average 12–16), so the
backend was not the bottleneck. These runs are reported only to show the order of
magnitude of the headroom; the authoritative comparison is the fixed-rate table
above, which is not saturated (load average 1.1–1.8 for the cached runs).

## Limitations

- Results are **environment-specific** to the 2-vCPU VPS described above; a
  different machine, dataset size, or PostgreSQL configuration will differ.
- The uncached aggregate queries are CPU-bound on this box, so the baseline
  load average saturates (~4–5 on 2 vCPUs) even at the chosen 15 req/s. The
  baseline p50 (~120 ms) matches its single-request latency (~110 ms), i.e. it is
  at capacity but not queueing-dominated at the median.
- The cached runs were not saturated (load average 1.1–1.8).
- Results are the median of three runs each; run-to-run variance is low but
  non-zero (see the per-run tables).
- Cache invalidation relies on `@CacheEvict` firing when the mutation returns,
  just before the transaction commits. A narrow race exists where a concurrent
  reader could repopulate the entry with pre-commit data; the 60 s TTL bounds how
  long that could persist.
