# SyncDesk performance benchmark (k6)

Reproducible k6 benchmark for the cached dashboard metrics endpoint
(`GET /api/dashboard/metrics`). It compares three situations that must not be
conflated:

1. **Baseline** — caching disabled entirely (every request hits PostgreSQL).
2. **Redis cold cache** — the first request after the cache is emptied.
3. **Redis warm cache** — sustained load served from the cache.

Full methodology, environment details and measured results live in
[`../docs/performance-benchmark.md`](../docs/performance-benchmark.md).

## Prerequisites

- Docker (PostgreSQL + Redis run as containers).
- `k6` (`k6 version`).
- Java 21 and the Maven wrapper (uses `./mvnw`).
- The backend needs a `JWT_SECRET` (>= 32 chars).

Check the machine before benchmarking (record these in the results):

```bash
nproc
free -h
k6 version
docker info --format '{{.ServerVersion}}'
```

## 1. Start PostgreSQL + Redis

```bash
docker compose -f docker-compose.db.yml up -d
```

## 2. Seeded dataset

The benchmark uses a **100,000-ticket** dataset (plus comments), generated by the
existing `DataSeeder` via a single `generate_series` insert. The seed size is
configurable; the default remains 500k for normal local/dev use.

Start the backend **once** to let it seed, with:

```bash
cd backend
# The JWT signing key must be base64 (any 32+ byte base64 value works), e.g.:
export JWT_SECRET=$(openssl rand -base64 32)
export SYNCDESK_SEED_TICKET_COUNT=100000
./mvnw spring-boot:run
```

Wait for the log line `Seeding completed in ... ms.` (and the comment seeding),
then stop the application.

## 3. Run the benchmark

Run each scenario **at least three times** and keep the representative median.
Never compare runs with different datasets, offered load, or machine load.

The default profile is a **constant-arrival-rate of 15 req/s** (tune with
`RATE`), which is the highest offered load the *uncached* backend sustains
without saturating on a small VPS — so the same profile is fair for both
scenarios. `PROFILE=vus` (`VUS=20`) switches to a saturating constant-VU profile
used only to observe maximum throughput; on a small box it will saturate.

```bash
# default: 15 req/s, warm-up + sustained
k6 run performance/dashboard.js

# saturating throughput observation
PROFILE=vus VUS=20 k6 run performance/dashboard.js
```

Representative summaries from the recorded runs are in
[`results/`](results/); full methodology and results are in
[`../docs/performance-benchmark.md`](../docs/performance-benchmark.md).

### Baseline (cache disabled)

```bash
cd backend
export JWT_SECRET=$(openssl rand -base64 32)
SYNCDESK_SEED_TICKET_COUNT=100000 SYNCDESK_CACHE_ENABLED=false ./mvnw spring-boot:run
```

(`SYNCDESK_CACHE_ENABLED=false` disables the cache entirely — no `@EnableCaching`,
so every request goes to PostgreSQL. Redis does not need to be running.)

In another shell:

```bash
k6 run performance/dashboard.js
```

### Redis cold cache

Start the backend normally (caching enabled, Redis up), then flush Redis and run
the single-request cold scenario:

```bash
docker exec syncdesk-redis-dev redis-cli FLUSHALL
SCENARIO=cold k6 run performance/dashboard.js
```

### Redis warm cache

```bash
docker exec syncdesk-redis-dev redis-cli FLUSHALL   # start from a cold cache
k6 run performance/dashboard.js                     # warm-up + sustained load
```

### Optional: cache hit ratio

```bash
docker exec syncdesk-redis-dev redis-cli INFO stats | grep keyspace
```

## 4. Record results

Capture `http_reqs` (RPS), `http_req_duration` p50/p95/p99 and
`http_req_failed` (error rate) from each run and update
`../docs/performance-benchmark.md`. Small representative summaries may be
committed under `results/`; do not commit large raw k6 output.

## Notes

- The baseline and cached runs use the **same artifact, dataset, endpoint,
  credentials, VUs and duration**. Caching is toggled with a property
  (`syncdesk.cache.enabled`), not a code change.
- If the machine becomes CPU/RAM saturated, **reduce the VUs** rather than
  benchmarking an overloaded host.
- Stop unrelated containers/processes before measuring.
